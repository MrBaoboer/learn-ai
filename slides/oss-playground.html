08b · 事实卡
类名 .oss-fact-card。用来陈述一组「已核实 / 尚未落实」混在一起的事实。 刻意做得朴素：这类内容一旦配上重样式，读者会以为在强调某个结论， 而这里要传达的恰恰是「事情还没定，别急着下结论」。 每一条都该是能核对的陈述，不确定的部分要写明不确定，不要用形容词补足分量。

08b-3 · 选材说明
类名 .oss-why。全章反复用同一个品牌举例时，把选材理由摆到明面上。 样式刻意做轻，浅底无阴影，不能比正文抢眼——它是一段交代，不是一个卖点。 写法上有三条硬要求：理由必须是可核对的事实而非形容词；至少写进一条对该品牌 不利的事实；结尾要说清「用它举例不等于它最好」。全章只在开头出现一次。

这一章的例子基本都取自某系列，先说清楚为什么。

  • 尺寸铺得最全。官方库里从最小档一直排到最大档，中间没有断层，每讲到一档设备都能对应上一个真能下载的文件。
  • 别人拿它当底座。第三方发布的衍生版本多数选它，这是别人的选择，不是自家宣传。
  • 它自己就是个反面教材。早期版本用过非标准许可证，正好拿来讲「开源」这两个字有多不可靠。

社区里有戏称，但那是网友的叫法，不是评价标准。拿它举例是因为素材齐、方便动手，不是因为它最好。

08b-4 · 量化刻度尺与排序翻转
类名 .qz-ruler / .qz-vals / .qz-cands，用在 oss-8。 解决的问题是「位数少了会有损失」这句话读者记得住却用不上，不知道该选哪一档。 刻度尺是核心：INT4 的 16 道刻度肉眼可数，INT8 密到只能画成条带， 两档的差距不用解释就看得见。档位超过 64 就切 .is-dense 走背景条带， 再密画下去只是一片黑，既慢又不诚实。 红点表示被抹成 0 的权重，多个权重落到同一位置是要的效果，不是 bug—— 那正是「不同的值被挤进同一个档位」这件事本身。 候选列表里 .is-top 的优先级必须高于 .is-moved， 否则扰动后四行一起变橙，看不出到底谁上了位。 数值全部来自 oss-calc.js 的量化函数，不要在页面里写死好看的数字， 这几个数读者是能自己验算的。

08c · 反馈动效（点按钮看效果）
统一走 OSSInteract.fire(el) 加一次性 .fire 类，动画结束不会自动摘除， 所以连续触发前必须先 remove 再强制重排 —— 这一步已经封在 fire 里，页面不要自己加类。 需要「只在状态真的变了才闪」时用 fireOnChange(el, key, store, slot)， 它比对上一次的 key，相同就不播，避免滑块每动一格整块都在抖。 reduced-motion 下 JS 与 CSS 两处都会拦截，缺一处会让这类用户白等一个动画时长。
