思路一 · 注入先變成型別
它解決什麼問題

你給 agent 加過這類功能：使用者剛批准了 npm *，下一輪模型還在問要不要跑 npm test。或者壓縮剛結束，模型突然忘了工作區在哪、沙箱是只讀還是可寫。再或者 fork 一條會話，舊的 AGENTS.md 還在，新的目錄提示疊上去，模型同時看見兩套互相打架的規則。

這三件事的共同來源是同一類操作：執行時往模型上下文裡塞了一段文字。批准前綴、工作區、權限檔案、被中斷的 turn、當前 UTC 時間，全是告訴模型一件它自己看不到的事實。一段 format! 就能寫出來。

問題出在事後。這段文字進了歷史之後，壓縮要不要留它、會話恢復要不要認它、UI 要不要把它藏起來、world state 要不要拿它當模型已經知道了的證據，全都依賴一件事：你還能從純文字裡把它認回來。各處再寫一遍 startsWith，過幾週四處會漂。未知標籤還會漏進使用者訊息解析。

思路是什麼

Codex 把每一種注入收成一個實現 ContextualUserFragment 的型別。trait 不在 codex-core 裡，而在獨立 crate codex-context-fragments。每個實現必須同時回答：這段以 user 還是 developer 進 Responses API，頭尾 marker 是什麼，中間 body 怎麼寫，要不要單獨成一條訊息。

render() 把頭尾 marker 和 body 直接首尾相接，中間不加分隔符。空白和換行算 body 的。空 marker 只輸出 body。into() 把渲染結果收成一條 ResponseItem::Message，content 只有一個 InputText。注入的終點是協議物件。

codex-rs/context-fragments/src/fragment.rs第 38 至 46 行
    fn render(&self) -> String {
        let (start_marker, end_marker) = self.markers();
        let body = self.body();
        if start_marker.is_empty() && end_marker.is_empty() {
            return body;
        }

        format!("{start_marker}{body}{end_marker}")
    }
原始碼快照說明：依據本地倉庫 openai/codex，核對檔案 codex-rs/context-fragments/src/fragment.rs，commit 4f39251a01，核對日期 2026-08-22。程式碼塊保留原始碼原文，這段就是型別把自己收成一段可注入文字的全部規則。

markers() 帶 self，渲染走例項。type_markers() 不帶 self，識別走型別。手裡只有歷史文字、沒有原物件時，仍然能問這段像不像某某 fragment。dyn ContextualUserFragment 調不了 matches_text，反向識別必須點到具體型別。

加一種注入要新建檔案、實現 trait、掛進 core/src/context/mod.rs。目錄裡 39 個模組。這個摩擦力本身就是治理：臨時 format! 走不通，因為組裝函式收的是 Box<dyn ContextualUserFragment>。出處：codex-rs/core/src/context/mod.rs 第 3 至 41 行；codex-rs/core/src/session/mod.rs 第 3677 至 3707 行

教學化結構圖：渲染走例項，識別走型別，兩套呼叫讀同一對 marker。
為什麼長期成立

渲染和識別共用一份定義。換個語言重寫，最小形態仍是一份介面、一份登錄表、同一對 marker。組裝函式的參數寫成 fragment 型別，業務側就失去了隨手拼 XML 的呼叫點。識別函式只從登錄表做匹配，不許再寫一套 text.startsWith。

思路二 · 有標和無標要寫清楚
它解決什麼問題

所有注入都帶標，一次性通知也會在壓縮後被重認、再喂一遍。所有注入都不帶標，壓縮後的歷史裡分不清使用者原話和執行時塞進去的說明。fork 會把過期的 <environment_context> 當成使用者輸入重新提交。

思路是什麼

視窗身份、環境、中斷、圖片縮放、管理側開發者指令，事後要認、要 diff、要在壓縮後決定是否重注，所以帶 begin 和 end。一次性通知，比如批准前綴、網路規則入冊、剩餘 token 一句提醒，type_markers() 返回兩個空串。預設 matches_text 恆為 false。

匹配規則只看整段文字的首尾。先 trim 開頭比前綴，再 trim 結尾比字尾，ASCII 大小寫不敏感，兩個都中才算命中。中間夾什麼不管。無標 fragment 主動放棄可逆性。出處：codex-rs/context-fragments/src/fragment.rs 第 89 至 103 行

developer 側另有一張前綴表，在 event_mapping.rs，用來補一部分無標識別。覆蓋面比 user 側 matcher 列表窄。前綴表裡至今留著 <token_budget> 舊標籤，註釋寫明是為了認舊版本持久化下來的包裝。marker 一旦寫進 rollout，就變成恢復合同的一部分。改標籤等於改協議。

UserInstructions 有一處容易看走眼。它的 begin marker 是 Markdown 標題 # AGENTS.md instructions，end marker 是 </INSTRUCTIONS>。協議裡另有 <user_instructions> 那對標籤，這個 struct 沒用。按協議常量去寫 matches_text，會認漏倉庫裡真實渲染出來的文字。出處：codex-rs/core/src/context/user_instructions.rs 第 18 至 19 行；codex-rs/protocol/src/protocol.rs 第 112 至 113 行

教學化對照：需要壓縮後重認的做成協議，一次性通知主動放棄可逆。
為什麼長期成立

需要事後認的做成協議，一次性的主動放棄，並且在型別上寫清楚。壓縮後要重認的強制 begin 和 end，一次性通知可以無標，但要在註釋裡寫放棄可逆。

思路三 · 組裝按型別欄位分揀
它解決什麼問題

各處隨手 push 字串，順序靠約定，單獨成條靠註釋。TokenBudgetContext 會和權限說明擠在同一條 developer 訊息裡。壓縮濾網沒法按條處理。混裝之後回滾也拆不開。event_mapping.rs 的註釋承認：build_initial_context 可能把 contextual fragment 和持久 developer 文字捆在一起。出處：codex-rs/core/src/event_mapping.rs 第 69 至 71 行

思路是什麼

第一次組裝發生在 Session::build_initial_context_with_world_state。它把 fragment 按 role()、markers() 的開頭、requires_separate_message() 分進幾組：可合併的 developer 段、必須單獨成條的 developer 段、user 段，以及要置頂或置底的特殊段。

視窗身份這一條有點特別。Feature::TokenBudget 開啟且模型有 context window 時，它在 world_state 迴圈之前就被推進單獨組。輸出順序是：先一條合併好的 developer 訊息，再一條條單獨的 developer 訊息，再一條 contextual user 訊息。分揀依據是型別欄位。出處：codex-rs/core/src/session/mod.rs 第 3630 至 3728 行

requires_separate_message() 把能不能和別人擠在同一條 developer 訊息裡也收進型別。TokenBudgetContext、ImageResizeNotice、ManagedDeveloperInstructions 選擇單獨成條。單獨成條的代價是多佔一條訊息、多一次 role 切換。好處是壓縮濾網可以按條處理。

教學化分揀圖：輸出順序是合併 developer、單獨 developer、contextual user。
點進模型輸入的任意一段，都能回到某個 fragment 型別。
為什麼長期成立

組裝入口只收已登記型別。這是把沒登記的注入擋在門外的通用形狀。型別擋得住沒登記，擋不住登記了但每輪塞 40KB。那一層是評審規則，下一章展開。

橫向對比 · 同一道題的另一種答法

閘開在哪：DeepSeek Harness 選擇發請求時對帳

DSH 寫在倉庫根 AGENTS.md 第 107 行，中文原則收成「模型可見即已記錄」。抵達模型請求的一切都必須能從會話日誌重建，新增一項模型可見輸入就需要新增一個會話事件。

執行面是 invariant.ts。它在 llm/stream 上掛監聽，從 session 日誌 deriveMessages() 得到期望值，再和即將發出的 options.messages 做 JSON.stringify 比較，對不上就 fail。閘開在崩潰點，能抓住組裝之後又改了 messages 這類只有執行時才出現的漂移。關掉 invariants 服務，這道閘就沒了。

真源不同：事件日誌，還是封閉的型別集合

DSH 可以沒有 fragment trait，因為它的真源是事件日誌，messages 是投影。Codex 把能出現在上下文裡的東西先收成封閉的型別集合，再用 marker 做事後識別。

代價也不同。Codex 的型別擋得住沒實現 trait 就塞進 render_full，擋不住 impl 裡面 format! 出來的動態字串。matches_text 認的是文字形狀。兩邊都為可追溯付錢，一個付在每次請求的斷言，一個付在每次加註入的型別摩擦。

認漏的會是哪一段

UserInstructions 的 begin marker 是 # AGENTS.md instructions，協議常量卻是 <user_instructions>。如果有人按協議常量去寫 matches_text，會認漏現在倉庫裡真實渲染出來的哪一種文字？

再推一步：把上面演示裡的批准前綴開啟，壓縮之後預設 matches_text 還能不能把它認回來。developer 側要靠哪張表補這一刀，改錯常量時編譯器會不會響。

Takeaway：往模型上下文裡塞的每一段，先收成一個型別，型別自己知道 role、marker 和 body。需要事後認的帶 begin 和 end，一次性通知主動放棄可逆。組裝按型別欄位分揀，沒登記的字串進不了信封。
