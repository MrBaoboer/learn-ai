Q1技術同事
「你天天説 Coding Agent，它一輪循環裏到底發生了什麼？別拿 PPT 那套糊弄我。」
🎯 對方在考察什麼
試探你是把 Agent 當黑盒，還是真的理解運行時。答「大模型加工具循環唄」這種一句話就露餡了。對方想聽你順着調用鏈，把幾個關鍵組件的分工講清楚。
🧭 答題框架
  1. 從入口講起：用 Grok Build 舉例，真實入口在 main()，按運行分支分發（headless、stdio、leader、交互 TUI），最後都匯到同一個 Agent 宿主。
  2. 三個 Actor 分工：SessionActor 負責 turn 編排，接收命令、啓動待處理 turn、處理完成通知；ChatStateActor 獨佔對話狀態；SamplerActor 負責流式的模型請求。
  3. 隔離單位：每個 Session 跑在獨立 OS 綫程上，帶自己的 current-thread Tokio runtime 和 LocalSet。會話之間天然隔離，一個卡死拖不垮別人。
  4. 收尾機制：用戶點停止靠 CancellationToken 協作式終止，各 Actor 有序退出，這就是取消邊界。
⭐ 加分點能説出「對話狀態由 ChatStateActor 通過消息隊列串行獨佔，所以不需要共享鎖」這一句，技術同事會立刻知道你真讀過架構，後面的合作態度都會不一樣。
用這些課程頁組織答案 → 從 main() 到第一輪採樣 Session Actor 與取消邊界 79 個 Workspace 成員
Q2面試官
「Coding Agent 動不動跑幾十輪，上下文很快就滿了。生產級產品是怎麼扛住的？」
🎯 對方在考察什麼
考你對上下文預算的工程化理解。只會説「把歷史壓縮一下」的人露餡：對方想聽觸發閾值、判斷邏輯、預算控制這些能落地的機制，這是 demo 和產品的分水嶺。
🧭 答題框架
  1. 先給觸發機制：以 Grok Build 為例，預設在上下文使用率達到 85% 時允許自動壓縮。判斷公式是 used × 100 >= context_window × threshold_percent，純整數比較。
  2. 壓縮本身要限時：單次壓縮有 300 秒的牆鐘預算。壓縮是為了救會話，自己耗時失控就本末倒置了。
  3. 講可選能力：memory flush 和 two-pass 預設都關閉。two-pass 開啓後，接近閾值時先在後台投機摘要歷史前綴，正式壓縮時再把摘要和近期尾部合併總結。
  4. 拔高一層：這些都收在 CompactionPolicy 一個顯式配置對象裏，閾值、壓縮模型、預算全部可調。生產級系統把策略做成配置，demo 把策略寫死在程式碼裏。
⭐ 加分點主動指出 Token 用量是估算值，閾值比較用飽和乘法防溢出、窗口為 0 時直接返回 false。能講到這種邊界處理，説明你看過真實實現，這在 PM 裏鳳毛麟角。
用這些課程頁組織答案 → Compaction：85% 閾值與 two-pass 估算、百分比與嚴格閾值
Q3面試官
「讓你給 Coding Agent 規劃工具集，幾十個工具怎麼管？哪些能直接跑，哪些要用戶點頭？」
🎯 對方在考察什麼
考工具系統的設計能力。張口就説「每個工具單獨配一遍權限」的人露餡了，幾十個工具根本配不過來。對方想聽分類學、預設語義和分層控制這套體系化思路。
🧭 答題框架
  1. 先給分類學：Grok Build 用 ToolKind 枚舉給工具定語義種類。讀文件、搜索、網頁抓取這類種類預設只讀；編輯、刪除、執行命令這類預設有副作用。
  2. 預設值可覆蓋：is_read_only() 只是種類層的預設語義，具體工具可以用自己的元數據覆蓋，分類和個體解耦。
  3. 説清關鍵邊界：只讀分類推不出「自動執行」。最終放行還要過命令規則、沙箱、Hook 和用戶交互批准這幾層，分類只是決策的第一個輸入。
  4. 補上註冊機制：內置工具走靜態註冊表，外部 Toolset 走進程級 Preset 註冊，MCP 工具運行時動態發現。三類來源統一收口，管理成本才不會爆炸。
⭐ 加分點舉 Task 這個反例：子任務聽起來無害，源碼把它標為非只讀，因為子 Agent 可以執行寫操作。能講出這種邊界 case，説明你真的過了一遍分類表。
用這些課程頁組織答案 → ToolKind 與只讀語義 Toolset Preset 註冊表 實現族、註冊表與動態 MCP
Q4技術同事
「Agent 的記憶，説白了就是把聊天記錄存文件裏，用的時候 grep 一下吧？」
🎯 對方在考察什麼
挑釁式提問，試探你懂多少檢索工程。順着説「差不多」就掉坑裏了。對方想聽召回路徑、降級策略和排序細節，這些決定記憶系統好不好用。
🧭 答題框架
  1. 先糾正前提：生產級記憶是一條檢索流水綫。以 Grok Build 為例，查詢前先同步髒文件：watcher 監聽 Markdown 變更，搜索開始時重建對應索引，外部修改才不會丟。
  2. 雙路召回：FTS5 BM25 關鍵詞檢索始終可用，向量 KNN（sqlite-vec）在 embedding 可用時疊加。embedding 失敗只記 warning，自動降級成 FTS-only，整次搜索照常返回。
  3. 排序有講究：雙路分數各自歸一化後加權合併，再乘時間衰減（session 記憶按半衰期衰減，global 和 workspace 視為長青）、來源權重和訪問增益。
  4. 多樣性可選：MMR 重排預設關閉，開啓後按相關性與 snippet 差異度做貪心重排，最後截斷到 max_results。
⭐ 加分點補一句後台還有 Dream 機制：空閒門控觸發，用 DreamLock 防併發，後台整理記憶再寫回。説明記憶系統有讀也有寫維護，你看到的是完整閉環。
用這些課程頁組織答案 → 從文件變更到混合排序 Dream 的真實機制 Token 估算與閾值
Q5老闆
「你要推全員用 Coding Agent？它要是把程式碼庫刪了，或者把源碼傳出去，這責任誰來擔？」
🎯 對方在考察什麼
考期望管理加機制理解。拍胸脯説「絕對安全」的人最危險；只會説「有沙箱」也不夠。對方想聽分層防護的具體方案，以及你敢不敢誠實交代邊界。
🧭 答題框架
  1. 先給結論：風險可控，核心是內核級沙箱。Grok Build 內置五種 Profile：workspace（預設）、devbox、read-only、strict、off，各自定義文件讀寫和子進程網絡的能力集合。
  2. 講機制：約束落在操作系統層，macOS 走 Seatbelt、Linux 走 Landlock。真實邊界看解析後的能力集合，Profile 名字只是方向。
  3. 給推廣方案：按人羣配 Profile。程式碼審查用 read-only，高敏感倉庫用 strict，還能配 custom profile 額外 deny 掉 ~/.ssh 這類目錄。項目配置無法悄悄覆蓋全局同名策略，安全底綫握在管理員手裏。
  4. 誠實交底：平台不支持或應用失敗時，沙箱會記錄警告繼續運行。所以要疊加權限審批和 Hook 審計做分層防護，沒有單點銀彈，責任靠制度加機制共擔。
⭐ 加分點主動分清兩層：Hook 是 fail-open 的，Hook 自己崩了工具照跑，所以它只適合提醒和審計；強制性保證必須放在權限層和沙箱。能把這兩層説清楚的人很少。
用這些課程頁組織答案 → 五種沙箱 Profile 從工具請求到受限執行 Hooks：明確 deny 才阻斷
Q6技術同事
「接個 MCP Server 不就是加兩行配置的事？這活你怎麼還給排了一個迭代？」
🎯 對方在考察什麼
反向試探你對生態集成工程量的判斷。以為「協議通了就完了」的 PM，排期一定翻車。對方想聽協議外圍那一堆髒活，你説得越具體，排期越有説服力。
🧭 答題框架
  1. 先對齊角色：Grok Build 是 MCP 客户端，要同時支持 stdio 和 Streamable HTTP 兩種傳輸，外加 OAuth：憑據存本地 JSON 文件，文件鎖配合原子寫防多進程衝突。
  2. 命名與衝突：工具註冊名是 server__tool，雙下劃綫恰好出現一次。兩個 Server 各有一個同名工具時，各自拿到不同 ToolId，模型側才不會打架。
  3. 可見性分流：工具多了不能全塞提示詞。禁用的、只給 UI 用的、模型可見的分三路處理，快照加 BM25 索引讓模型按需搜索工具。
  4. 斷綫恢復：狀態事件在 50 毫秒窗口內合併，stdio 重啓按 1 秒、4 秒、16 秒退避，還要靠 client_id 護欄防止舊連接的斷綫事件誤刪新連接。
⭐ 加分點一句話收尾：MCP 集成的工程量集中在協議外圍，命名、可見性、身份、狀態合併和恢復策略決定連接能否長期穩定。這就是排一個迭代的原因，技術同事聽完會主動幫你補細節。
用這些課程頁組織答案 → MCP 連接、發現與恢復 動態 MCP 工具 Plugin Marketplace 與信任

🎯 對方在考察什麼
這題埋了陷阱：「確定的答案」根本不存在。對方在看你有沒有證據邊界意識，會不會把合理解釋包裝成官方事實。張口就替 xAI 代言動機的人，做競品分析也一定摻水。
🧭 答題框架
  1. 先立規矩：把結論分成「源碼事實」和「課程推斷」兩套標籤。源碼能證明的：edition 設為 2024、Tokio 1 開啓 full feature、名為 xai-grok-pager 的原生 bin target、release-dist 裏的 LTO 和 panic 配置。

⭐ 加分點面試官要的正是第 3 步。敢在壓力下説「這個問題源碼回答不了」，比編一個漂亮答案值錢得多，這就是產品經理的證據素養。

Q8技術同事
「用 Rust 寫 Agent 圖什麼？編譯半天，招人還難。我拿 TypeScript 兩週就糊一個出來。」
🎯 對方在考察什麼
試探你是跟風吹 Rust，還是能説出可驗證的工程收益。同時看你敢不敢承認代價，只會捧不會講取捨的 PM，技術團隊不會真心配合。
🧭 答題框架
  1. 先認帳：編譯時間、生命週期約束、學習門檻都是真實代價，源碼課也是這麼標註的，沒必要嘴硬。

Q9面試官
「同一個讀文件工具，你們程式碼裏居然有好幾套實現。這也叫架構？改一個 bug 要改幾遍？」
🎯 對方在考察什麼
考多協議兼容的程式碼組織。對方故意把「實現族」説成重複程式碼，看你能不能講清這是命名空間隔離，以及一條工具從定義到執行的完整流水綫。
🧭 答題框架
  1. 先正名：這是按協議劃分的實現族。xai-grok-tools 裏平行放着 grok_build 主產品族、grok_build_concise 精簡族、grok_build_hashline、codex 和 opencode 兼容族，memory、lsp、skills 按能力單獨拆模組，namespace 枚舉裏還有 MCP 留給運行時外部工具。
  2. 組裝有流水綫：ToolRegistryBuilder 負責實現選擇和參數重命名，finalize(config, context) 產出 FinalizedToolset，裏面裝着 definitions、resources 和 dispatch。
  3. 會話接入一個口：ToolBridge 持有 registry，把工具定義提供給模型，調用結果以 ToolOutput 交回會話。MCP 工具運行時經 register_mcp_tools 註冊進同一個 registry，和內置工具共用執行通道。
  4. 回應質疑：兼容另一套 harness 是換一族實現的配置問題。真要所有協議共用一份程式碼，兼容邏輯會把每個工具都攪成 if 森林，那才是改一個 bug 要改幾遍。
⭐ 加分點提煉一句分層：實現族解決多套協議的程式碼組織，registry 負責組合與運行時註冊，ToolBridge 連接會話。三層各管一事，新加一族協議支持時，執行鏈路一行不用動。
用這些課程頁組織答案 → 實現族與動態 MCP ToolKind 與只讀語義

Q11面試官
「你們產品的 system prompt 是怎麼管理的？綫上出了怪行為，怎麼排查是哪段指令惹的禍？」
🎯 對方在考察什麼
考 prompt 的工程化管理。答「維護一個大字串模板」的人還停在作坊階段，對方想聽結構化、可檢查、可回放的方案。
🧭 答題框架
  1. 給結構化答案：Grok Build 用 PromptContext 結構體保存全部渲染輸入，帶 Serialize 和 Deserialize derive，能整體序列化下來檢查。排查看的是數據，猜的成分就少了。
  2. 字段分三組：版本與模板（version、prompt_mode、audience、build_timestamp_utc），配置與身份（agents_md_files、persona_summaries、role_instructions、memory_enabled），用戶運行環境（os_name、shell_path、working_directory、current_date）。
  3. 渲染分工：TemplateOverride 決定基礎模板，ToolBridge 提供工具狀態和描述，TemplateRenderer 合成各個 section，輸出最終 system prompt。
  4. 更新邊界：Agent 構建後源碼註釋稱「effectively immutable」，但保留 finalize_prompt 這個顯式入口，更新構建時間戳後重新渲染。

  2. wrapper 也算過：解析會遞歸剝離包裝層拿到實際命令，危險前綴名單裏有 rm、chmod、chown、kill 和 git push。

⭐ 加分點點出這套設計最容易被低估的地方：按腳本結構做權限決策。用正則匹配命令字串的方案在 shell 語法面前全是洞，語法樹解析才是正解。

Q24面試官
「用戶批准了一次 rm，這個會話之後是不是就能隨便刪文件了？把你們的授權模型完整講一遍。」
🎯 對方在考察什麼
考授權鏈全貌和兩層邊界。只答「彈窗確認」的人對安全的理解停在 UI 層，對方想聽決策輸入、規則優先級和沙箱兜底怎麼疊起來。
🧭 答題框架
  1. 先答問題本身：批准只放行本次請求。授權決策的輸入是 AccessKind，工具輸入被解析成 Read、Edit、Bash、MCPTool 這類帶具體路徑和命令的訪問意圖，比 ToolKind 更細。
  2. 走一遍鏈路：plan gate 先攔編輯，PreToolUse hook 可以顯式 deny，然後 permission manager 評估合併後的規則。規則優先級是 deny > ask > allow，和配置來源順序無關。
  3. 決策快速路徑有序：管理策略的 deny 最先短路，隨後才輪到 yolo pin、session grants、Auto 判定、sandbox Bash auto、只讀安全項，都沒結論才彈窗問用戶。
  4. 補第二層：權限層的 Allow 不擴大操作系統能力。沙箱 active 時，進程仍被能力集合和子進程網絡策略框着。權限層決定「能否嘗試」，沙箱層限制「能做到什麼」，疊加才是完整邊界。
⭐ 加分點主動糾正一個流傳很廣的説法：「沙箱內所有寫操作自動批准」是錯的。sandbox fast path 只檢查 Bash，還受 policy_forced_prompt 和 auto_forced_prompt 約束。

「安全團隊要全公司統一沙箱策略，項目組又想自己加規則。配置系統怎麼設計才不打架？」
🎯 對方在考察什麼
考配置分層治理：誰能改什麼、衝突聽誰的、怎麼防止項目組悄悄放寬安全底綫。這是企業產品繞不開的設計題。
🧭 答題框架
  1. 給合併規則：Grok Build 先讀全局 ~/.grok/sandbox.toml，再讀項目 .grok/sandbox.toml，合併用 entry.or_insert。項目只能新增 profile 名稱，聲明瞭和全局同名的 profile，全局定義保持生效，項目改不動。
  2. 給擴展方式：項目自定義走 custom profile，預設從 workspace 起步，extends 只能選 workspace、devbox、read-only、strict 四個內置基類，read_only、read_write、deny 往基類上追加。
  3. 給兩條禁令：不能 extends off 和 none，也不能 extends 另一個 custom。禁掉鏈式繼承，安全審計才能沿一條綫看清最終能力。

⭐ 加分點點出 entry.or_insert 一行程式碼就是治理模型：先加載的贏。把「全局優先」做成合並語義，比做成審批制度可靠得多，這是用機制代替流程的範例。

Q26老闆
「團隊想從插件市場裝一堆社區插件提效。萬一裏面藏咗個惡意嘅，將我哋嘅程式碼偷跑咗點算？」
🎯 對方在考察什麼
考插件生態的信任設計。只會説「裝之前審核一下」的人扛不住追問，老闆想聽系統層面有幾道閘，以及閘門失效時會發生什麼。
🧭 答題框架
  1. 給三道門：裝了不等於能跑。第一道是來源與路徑，MarketplaceRelativePath 拒絕絕對路徑和父目錄穿越，遠程條目能用 git ref 或 SHA 鎖定內容；第二道是啓用狀態，項目和用戶範圍發現的插件預設進 disabled 列表；第三道是執行信任，按插件根目錄逐個授權，記錄寫進 ~/.grok/trusted-plugins。
  2. 講未信任的待遇：skills 和 agents 只能露元數據，hooks 不加載、MCP server 不啓動、scripts 不執行。最危險的可執行面全被按住。
  3. 給失敗語義：插件根目錄 canonicalize 失敗直接按未信任處理，失敗關閉，路徑出問題也不會誤放行。
  4. 落到流程：高危插件先在 read-only 沙箱裏審閲內容再授信，遠程安裝用 SHA 固定版本，防止上游偷偷換包。
⭐ 加分點給老闆一句能記住的總結：發現、安裝、執行是三層，每層有獨立門檻。惡意插件要連闖三關，而且第三關預設是關着的。

Q27面試官
「用戶接了幾百個 MCP 工具，全塞進提示詞，上下文直接炸了。你怎麼設計？」
🎯 對方在考察什麼
考工具規模化的方案。答「做個開關讓用戶少開點」是在甩鍋給用戶，對方想聽延遲發現這套系統解法。
🧭 答題框架
  1. 給核心思路：工具元數據進 ToolMetadataSnapshot（tools、servers、mcp_initialized 三個字段），配 BM25 索引，不讓幾百個定義常駐提示詞。
  2. 給兩個穩定入口：模型側只暴露 SearchTool 和 UseTool。SearchTool 按關鍵詞搜，參數是 query 加 limit（預設 5），結果按 server 分組，帶描述和 input_schema；UseTool 收 tool_name 和 tool_input，按發現到的 schema 分發執行。
  3. 講穩定性收益：模型的工具列表跨輪次不變，幾百個工具的增刪不沖刷上下文，提示詞緩存也友好。
  4. 補分發細節：UseTool 收到合格工具名後走 InnerDispatch 或 managed gateway 調用 MCP。模型的用法是先搜到 input_schema，照着 schema 構造 tool_input 再調用，發現和執行徹底分開。
⭐ 加分點提 mcp_initialized 這個小字段：能力發現還沒完成時，搜索層知道「搜不到」和「還沒準備好」是兩回事，不會給模型一個錯誤的空結果。細節到這一層，沒人再懷疑你。

Q29面試官
「換你當面試官，別人交上來一份 Coding Agent 設計方案，你怎麼評分？」
🎯 對方在考察什麼
反向考察。你的評審標準暴露你自己的知識結構：看重什麼、忽略什麼、有沒有體系。只會挑功能毛病的人，評分體系撐不過三個追問。
🧭 答題框架
  1. 給量表：用結課評審的 100 分權重：邊界與 ADR 20 分、合約與狀態機 20 分、安全與恢復 25 分、測試與可觀測 20 分、演示與證據 15 分。安全與恢復權重最高。
  2. 給否決項：四條一票否決：敏感數據落點沒説明、高風險工具缺權限路徑、聲稱崩潰可恢復但沒有測試、引用源碼給不出文件路徑。分再高踩了也不過。
  3. 給檢查方法：拿九維決策卡過一遍：入口、狀態併發、模型流、工具合約、上下文記憶、安全、恢復、可觀測、擴展。每個維度要有明確決定、合約、故障路徑和驗證方式。
  4. 説明權重理由：功能是平時能看見的，安全與恢復是出事才看見的。評審就該把權重壓在「出事才看見」的地方。
⭐ 加分點引用一條評審哲學收尾：每項設計決定要能回到一個真實的失敗分支。説不出失敗預設值（停止、降級還是問用戶）的設計，都還停在 PPT 階段。
