멀티 Agent

언제 여러 Agent가 필요한가

Agent가 많을수록 좋은 것이 아닙니다. 대부분의 경우 하나로 충분합니다. 하지만 단일 Agent로는 감당하기 어려운 세 가지 시나리오가 있습니다. 언제 실제로 분업이 필요한지 파악하세요.

세 가지 실제 시나리오
⚡
병렬 가속
5개 소스를 동시에 검색하면 순차 검색보다 5배 빠름
클릭하여 사례 펼치기
실제 사례: 뉴스 브리핑
사용자가 오늘의 AI 뉴스 정리를 요청합니다. 단일 Agent가 5개 웹사이트를 순차적으로 검색하면 총 25초 소요됩니다.

5개 하위 Agent가 동시에 검색하고, 각 Agent가 하나의 소스를 담당하며, 최종적으로 주 Agent가 통합하면 총 5초가 소요됩니다.

핵심: 이 검색들은 서로 독립적이므로 자연스럽게 병렬화에 적합합니다.
역할 분담
하나는 코드 작성, 하나는 코드 리뷰, 상호 견제
클릭하여 사례 펼치기
실제 사례: 코드 리뷰
동일한 Agent가 코드를 작성하고 스스로 리뷰하게 하면, 마치 자기 글을 스스로 교정하는 것처럼 자신의 오류를 발견하기 어렵습니다.

두 Agent로 분리: Writer가 코드를 작성하고, Reviewer가 리뷰합니다. Reviewer는 Writer의 사고 과정을 모르고 최종 코드만 보기 때문에 문제를 더 잘 발견합니다.

핵심: 역할 격리로 리뷰가 실질적으로 효과적이 됩니다.
위험 격리
하위 작업의 오류가 주 작업에 영향을 주지 않음
클릭하여 사례 펼치기
실제 사례: 복잡한 문서 처리
주 Agent가 50페이지 보고서를 정리하고 있습니다. 이 과정에서 여러 PDF 첨부 파일을 파싱해야 합니다.

PDF 파싱이 실패(형식 오류, 타임아웃)하면, 주 Agent 내부에서 직접 처리하면 전체 작업이 충돌할 수 있습니다.

하위 Agent를 분리하여 PDF를 독립적으로 처리: 성공하면 결과를 보고하고, 실패하면 "이 파일에 문제가 있습니다"를 보고하며, 주 Agent는 영향 없이 계속 작업합니다.

핵심: 하위 작업의 실패가 격리됩니다.

판단 기준: 두 번째 Agent를 추가하기 전에 먼저 자문하세요:
① 단일 Agent로 정말 불가능한가요? (많은 경우 Prompt가 잘못 작성된 것일 뿐입니다)
② 추가되는 복잡도가 그만한 가치가 있나요? (멀티 Agent는 더 많은 조율 비용과 오류 가능성을 의미합니다)
③ 더 간단한 방법은 없나요? (예: 도구 병렬 호출로 해결 가능하다면 Agent를 분리할 필요가 없습니다)
Agent가 많을수록 좋은 것이 아니며, 대부분의 경우 하나로 충분합니다. 언제 실제로 분업이 필요한지 파악하세요. 병렬 가속, 역할 견제, 위험 격리 이 세 가지 명확한 요구가 있을 때만 멀티 Agent 도입이 가치 있습니다.
