POLICY TRADE-OFF

Hook 故障時優先工具可用性

Hook crash、timeout 與 bad output 採用 fail-open。這個選擇減少誤阻斷，也意味著強制安全規則需要權限層或沙箱共同承擔。

05 / SNAPSHOT

本次課程的四條適用邊界

B1

週期同步

結論對應公開快照，不能給內部 monorepo 的即時版本作證明。

B2

無外部貢獻

可以閱讀、構建與按許可證使用，不能把公開倉庫視為常規社群 PR 入口。

B3

根 Cargo 生成

依賴與 workspace 拓撲可能受生成流程控制，原始碼研究要追蹤 per-crate 清單。

B4

缺少 Git 中繼資料

本地 grok-build-main 快照未攜帶 .git 目錄，無法在該快照核心對 commit、tag、blame 與提交時間線。

結論口徑：B4 是本地檔案觀察，B1 至 B3 有倉庫文件支援。課程引用路徑與行為，不把無法定位的提交雜湊寫成證據。

07 / LAB

課堂練習：原始碼回顧審計

35 MIN

提交物
證據帳本

  1. 選擇三個優點，每項附一條原始碼路徑、一個關鍵分支和一條相關測試。
  2. 選擇三個限制，標註其屬於產品、倉庫、構建還是本地快照邊界。
  3. 刪除「生態大、社群強、體驗最好」等無法由當前材料證明的句子。
  4. 為 fail-open Hook 寫一個適用場景和一個不適用場景。
  5. 列出需要 release notes、線上文件或產品 PoC 才能回答的五個未知項。
Takeaway

高品質原始碼回顧要同時回答三件事：實現提供了什麼約束，倉庫以什麼方式發布，當前材料缺少什麼證據。限制寫清楚，優點才更可信。
