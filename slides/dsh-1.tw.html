一切皆外掛：官宣與原始碼對照

發布文裡說的四種模式、外掛生態，在 deepseek-harness 倉庫裡對應哪個檔案？本課一條條對上。

一句話速覽

把發布文案裡的四種模式、會話日誌、外掛生態逐條對到倉庫裡的 YAML 預設與包結構

課程目標讀完本課，你能把發布文裡的說法講成兩個思路：為什麼 DSH 把模型轉接器、工具乃至 agent loop 全做成外掛；為什麼官宣的四種模式在原始碼裡只是四份外掛清單。你還能說出 PTC 模式在原始碼裡的真名。

思路一 · 核心只管裝卸，業務全是外掛

它解決什麼問題。想像你在用一個單體架構的 Agent 產品，想換掉它的會話日誌格式。你得 fork 倉庫，在幾十萬行原始碼裡找到日誌實現，改完重新構建，之後官方每發一版你都要重新合併一次補丁。這還只是日誌這種邊角能力，要是想換 agent loop 主迴圈，基本等於重寫產品。能力和產品原始碼焊死在一起，任何深度客製都會變成長期維護負擔。

思路是什麼。DSH 把核心縮到最小。vendor 進倉庫的 Cordis 框架只做三件事：把外掛裝進共享上下文、把外掛卸下來、把每次註冊記成可逆的副作用，外掛解除安裝時自動回滾。業務邏輯一行都沒有。然後所有能力搬進 packages/，49 個分組、219 個包，全部以外掛形式存在：模型轉接器是外掛，工具是外掛，會話日誌是外掛，連 agent loop 主迴圈本身也是外掛。根 AGENTS.md 第 3 行用加粗英文寫著「everything is a plugin」。官方文件的原話：

Cordis 是 dsh 底層的框架：外掛向共享上下文貢獻服務、型別化事件和可逆的副作用。產品的每一部分都是外掛，包括模型轉接器、工具註冊表、會話日誌，以及 agent loop（智慧體迴圈）本身，因此每一部分都可以從配置替換。

不存在需要打補丁的特權核心：擴充 dsh 的方式是把外掛掛載到其他外掛旁邊，而各項註冊都是副作用，會在其外掛解除安裝時撤銷。

docs/architecture.zh.md · 第 11、13 行
教學化結構圖：分組歸類依據 AGENTS.md「Repository layout」與 packages/README.zh.md，內容經過課程化整理；包數為 2026-08-13 本地統計。

想給 DSH 加能力，也不用碰它的倉庫。樹外（out-of-tree，指官方倉庫之外的）外掛用 dsh plugin --profile <name> add <package> 裝進 profile，執行時掛載，解除安裝時註冊的副作用自動回滾。README 還約定外掛倉庫統一打 dsh-plugin 話題標籤，方便互相發現。發布文邀請大家共建生態，機制是現成的。

出處：packages/bundle/README.zh.md 第 13 行；README.zh.md 第 40 行；docs/architecture.zh.md 第 13 行

為什麼長期成立。微核心思想比這份程式碼老得多。作業系統課上的 Mach 和 L4，瀏覽器的擴充套件體系，VS Code 的外掛生態，走的都是同一條路：變化快的能力放外圈，幾乎不變的裝卸機制放核心。DSH 明年把 agent loop 重寫一遍，Cordis 的裝卸邏輯一行不用動；換個語言把整個 harness 再寫一遍，這個分層照樣管用。所以記這門課的結構比記它的程式碼划算，程式碼只是這個思路的某一版實現。

變化快的能力住在外掛裡，幾乎不變的裝卸住在核心裡。
思路二 · 模式就是一份清單

它解決什麼問題。多數產品的模式是硬編碼的：程式碼裡散著一堆類似 if (mode === 'lite') 的分支，模式數量在寫程式碼的那一刻就定死了。想新增一個模式，要改程式碼、過測試、等發版；想微調某個模式裡的一個能力，還是這套流程。使用者更沒得選，只能在官方給的幾個套餐裡挑。

思路是什麼。DSH 裡一個模式就是 apps/cli/config/agent-presets/ 下的一個目錄，目錄裡兩個檔案。preset.yml 只有 3 行，管 UI 上的展示名和排序；agent.cordis.yml 是外掛清單，啟動時 Cordis 照著清單逐行掛載，輸出一個組裝好的 Agent。切換模式就是換一份清單重新組裝，原始碼裡沒有任何模式分支。四種模式的差異，看四張卡就夠了：

順帶點破一個行銷詞。code/preset.yml 第 1 行寫 name: PTC 模式，但目錄叫 code，原始碼註釋和文件裡這套機制叫 Code Mode，全倉庫找不到名為 PTC 的實現。PTC 只活在 UI 文案層，跟人聊原始碼時說 Code Mode 才對得上號。

切換模式，就是換一份清單重新組裝。

為什麼長期成立。這條思路有個通行的名字，配置即架構：把系統之間的行為差異收斂進一份宣告式清單，架構問題就降維成文字問題。想知道兩個模式差在哪，diff 兩份 YAML；想造新模式，複製目錄改幾行；出了問題，回滾清單就行。Kubernetes 用 YAML 宣告叢集，Docker 用 Dockerfile 宣告映像，同一個思路在不同層面反覆出現。DSH 的外掛實現哪天全部重寫，清單這層抽象照樣成立。

橫向對比 · 加能力要不要改倉庫原始碼

一切皆外掛的價值放到同行裡才看得清。同一個問題，想給 Agent 加一個新能力，需不需要動它的倉庫原始碼，三家給出三種答案：

DSH：外掛樹

不需要改倉庫

能力就是一個樹外 npm 包。dsh plugin --profile <name> add <package> 裝進 profile，執行時掛載，解除安裝時註冊副作用自動回滾。模式級差異也只是 YAML 裡增刪幾行。

出處：packages/bundle/README.zh.md 第 13 行；docs/architecture.zh.md 第 13 行

Claude Code：產品單體

看情況

還原原始碼是一棵 TypeScript 單體原始碼樹（restored-src/src/，入口 main.tsx），改內建功能要動產品原始碼。對外留了 hooks、MCP、Skills 這些擴充點，能加工具和攔截點，換不掉會話日誌這類深層實現。基於已公開證據（還原原始碼目錄結構）。

Grok Build：Cargo Workspace

需要改倉庫

根 Cargo.toml 的 members 陣列列了 79 個 workspace 成員（本地計數），能力按 crate 切分、編譯期組合。新增能力要新建 crate、改根清單、重新編譯。切分細節見 12-1 · 79 個 Workspace 成員如何組成產品。

三家沒有絕對優劣。Grok 用編譯期組合換 Rust 的型別和效能保證，Claude Code 用單體換產品迭代速度，DSH 用外掛樹換執行時可拔插。只是如果你想要一個可替換、可審計的執行時，DSH 是三家裡唯一讓第三方無需 fork 倉庫就能替換深層能力的。

Takeaway：DSH 的核心只管外掛的載入、解除安裝與依賴，能力全部是 packages/ 裡的外掛。官宣的四種模式在原始碼裡是四份 agent-presets 外掛清單，切模式就是換清單重新組裝。PTC 這個名字只活在 preset.yml 的展示名裡，機制的真名叫 Code Mode。
